## Executive Summary

OpenClaw has substantial security infrastructure: CodeQL (`.github/workflows/codeql.yml`), Dependabot across 5 ecosystems with 7 directory entries (`.github/dependabot.yml`), `detect-secrets` with a 13,017-line baseline (`.secrets.baseline`), OIDC trusted-publishing for npm with verifiable provenance (`.github/workflows/openclaw-npm-release.yml:281-289, 366`), strict ws/wss enforcement (`src/gateway/connection-details.ts:66-80`, `src/gateway/net.ts:508-542`), CODEOWNERS gated to `@openclaw/secops` (`.github/CODEOWNERS`), pnpm `minimumReleaseAge: 2880` for 48h supply-chain soak (`pnpm-workspace.yaml:7`), and a bespoke dependency-ownership audit (`scripts/sbom-risk-report.mjs`, 314 lines, 172 ownership records).

It also has substantial complexity: ~7,025 TS files in `src/`, 109 extensions in `extensions/`, 28 GitHub Actions workflows, 314 root npm scripts, 8 release-related workflows, 5 application platforms (Node CLI, macOS, iOS, Android, Docker).

The trust model is **explicitly single-operator-trusted** (`SECURITY.md:98-122`). That is a documented product decision, not a finding. The findings below sit downstream of that decision: where attestation chains are missing, where static tokens could be ephemeral, where solo-maintainer load could be reduced through codified guardrails.

## 1. SBOM Lens

### What exists

- **Bespoke risk reporter** at `scripts/sbom-risk-report.mjs` (314 lines), tested by `test/scripts/sbom-risk-report.test.ts`. Schema is `schemaVersion: 1` over the pnpm lockfile. It tracks importer count, lockfile package count, root direct-dep count, root closure size, build-risk packages (`requiresBuild | hasBin | os | cpu | libc`), per-root-dep transitive closure sizes, and ownership gaps against `scripts/lib/dependency-ownership.json` (172 ownership records).
- npm scripts `deps:sbom-risk` and `deps:sbom-risk:check` exposed at `package.json:1345-1346`.
- Companion ownership audit `scripts/root-dependency-ownership-audit.mjs`.
- **Bundled-extension dependency tracking:** `scripts/stage-bundled-plugin-runtime-deps.mjs` + `scripts/runtime-postbuild.mjs` + `scripts/copy-bundled-plugin-metadata.mjs` + `scripts/test-built-bundled-runtime-deps.mjs`. Uses content-hashed stamps (`.openclaw-runtime-deps-stamp.json`). The published npm tarball excludes these directories via `package.json` `files` allowlist negative patterns (lines 32-34).
- **Lockfile pinning:** single root `pnpm-lock.yaml`, 15,460 lines, ~1,497 distinct package entries.
- **Override discipline:** 4 root `overrides` + 22 `pnpm.overrides` = 26 forced version pins. Many are CVE-driven (e.g., `request` → `@cypress/request`, `tough-cookie 4.1.3`, `tar 7.5.13`, `protobufjs 7.5.5`, `qs 6.14.2`).
- **`pnpm.patchedDependencies`:** 1 entry — `@whiskeysockets/baileys@7.0.0-rc.9` (`patches/@whiskeysockets__baileys@7.0.0-rc.9.patch`).
- **`pnpm.onlyBuiltDependencies`:** 10 entries (native build allowlist) per `pnpm-workspace.yaml`.
- **Supply-chain soak gate:** `pnpm-workspace.yaml:7` `minimumReleaseAge: 2880` (48h). Critical mitigation against fresh malicious publishes given the in-process plugin trust model below.
- **Dependabot:** 5 ecosystems × 7 directory entries (`/` for npm/github-actions/docker, `/apps/macos`, `/apps/shared/MoltbotKit`, `/Swabble` for swift, `/apps/android` for gradle), `cooldown: default-days: 2`, grouping by minor/patch + production/development.
- **Docker base images:** pinned by SHA256 digest (`Dockerfile:19-22`; `Dockerfile.sandbox:3` pins `debian:bookworm-slim@sha256:4724...`).

### What is missing

- **No SPDX or CycloneDX document** anywhere in the repository or release artifacts. `grep -r 'sbom\|cyclonedx\|spdx'` in `.github/workflows/` returns zero hits.
- **`deps:sbom-risk:check` is not invoked from any workflow.** The script exists, the test exists, the npm script exists — but `grep -rn "deps:sbom-risk:check\|sbom-risk-report" .github/` returns empty. Ownership-gap regressions cannot block merges today.
- **No SBOM in published artifacts:** the `package.json` `files` allowlist contains no `*.spdx.json`, `*.cdx.json`, or `bom.*` patterns. GitHub Releases include no SBOM assets.
- **No SBOM signing/attestation.** `actions/attest-sbom`, `actions/attest-build-provenance`, `cosign`, `sigstore`, `slsa-framework`, `in-toto` — none present in `.github/workflows/`.
- **Per-extension SBOMs not tracked.** The bundled-runtime-deps system has all the metadata to emit per-extension SBOMs but emits none.

### Risk classification

- **SBOM format absence: High** — EU Cyber Resilience Act vulnerability-reporting obligations bind 2026-09-11. SBOM in technical documentation binds 2027-12-11. OpenClaw is plausibly in scope as a network-connected developer tool. Lead time for tool adoption + first clean run + downstream-consumer testing is months, not weeks.
- **`deps:sbom-risk:check` not in CI: Medium** — the value is built; the wiring is missing. Cheap to fix.
- **No attestation chain on Docker/DMG: High** — see Zero Trust §2 below; this finding lives in both lenses.

## 2. Zero Trust Lens

### What exists (and is by-design)

- **Single-operator gateway trust model:** `SECURITY.md:98-122`. Shared-bearer auth grants full operator + owner-sender. Per-request `x-openclaw-scopes` is **explicitly ignored** under shared-secret. Narrower scope splitting only applies under identity-bearing HTTP modes (trusted proxy auth or `gateway.auth.mode="none"` on private ingress). Documented as not-a-bug in `SECURITY.md:60-65, 75, 132-153`.
- **In-process plugin trust:** `SECURITY.md:123-129, 223-229`. "Plugins/extensions are loaded **in-process** with the Gateway and are treated as trusted code… can execute with the same OS privileges as the OpenClaw process. Runtime helpers are convenience APIs, not a sandbox boundary."

These are documented product decisions and **not findings**. The audit calls them out so subsequent findings can be read against the right baseline.

### What exists (controls)

- **Secret store layout:** `~/.openclaw/credentials/` (channels/providers), `~/.openclaw/agents/<id>/agent/auth-profiles.json` (model auth), env vars in `~/.profile`. Documented at `AGENTS.md:137-139`.
- **In-repo secret scanning:** `.detect-secrets.cfg` + `.secrets.baseline` (13,017 lines). pnpm-lock excluded. Pre-commit via `.pre-commit-config.yaml` runs `detect-secrets` v1.5.0 + `detect-private-key` against staged files.
- **Secret-aware code:** `src/secrets/` (~110 files including `secret-value.ts`, `auth-store-paths.ts`, `storage-scan.ts`, `runtime-auth-*`, `legacy-secretref-env-marker.ts`). `src/security/` (~80 files) holds `audit*`, `dangerous-config-flags*`, `safe-regex.*`, `windows-acl.*`. Both CODEOWNERS-gated to `@openclaw/secops`.
- **Network posture:** strict-by-default. `src/gateway/connection-details.ts:66-80` rejects non-loopback `ws://` unless `OPENCLAW_ALLOW_INSECURE_PRIVATE_WS=1`. `src/gateway/net.ts:508-542` documents the policy. `src/pairing/setup-code.ts:75-79, 287` enforces `wss://` for Tailscale and public mobile pairing. Default gateway bind is loopback (`SECURITY.md:273`).
- **CI/CD trust:**
  - `.github/workflows/ci.yml:12-13` minimal `permissions: contents: read` at workflow level; elevated per job.
  - `.github/workflows/codeql.yml:15-18` same minimal-permissions pattern.
  - npm release uses **OIDC trusted publishing** (`openclaw-npm-release.yml:289` `id-token: write`), guarded `environment: npm-release` (line 285), dispatch-ref allowlist (lines 261-267), preflight-run-id verification (lines 269-339), tarball provenance verification (line 366).
  - Workflow-security scanner config exists: `zizmor.yml`.
  - 28 workflow files total; 49 explicit `permissions:` blocks across them.
- **CODEOWNERS:** 46 path rules in `.github/CODEOWNERS` gating `/SECURITY.md`, `/.github/dependabot.yml`, `/.github/codeql/`, `/src/security/`, `/src/secrets/`, `/src/config/*secret*.ts`, plus auth-related paths under `src/gateway/`, `src/agents/`, `src/infra/`, and `docs/security/`.
- **Sandboxing:** three sandbox Dockerfiles (`Dockerfile.sandbox`, `Dockerfile.sandbox-common`, `Dockerfile.sandbox-browser`). Default exec is host-first (`SECURITY.md:117-121`); sub-agent delegation supports opt-in `sandbox: "require"` (lines 261-267).
- **Plugin loader denylist:** `src/plugins/dependency-denylist.ts:1` — `BLOCKED_INSTALL_DEPENDENCY_PACKAGE_NAMES = ["plain-crypto-js"] as const`. Plus `plugins.allow` allowlist mechanism.
- **Plugin loader integrity awareness:** `src/plugins/install.ts` references `NpmIntegrityDrift` type — internal awareness of npm tarball integrity hashes.
- **macOS auto-update signing:** Sparkle EdDSA, key whitelisted in `.detect-secrets.cfg:45`. Application-level update signing (not artifact-level provenance).

### What is missing

- **Docker buildx provenance disabled in 10 places across 4 workflows:**
  - `.github/workflows/docker-release.yml` lines 164, 180, 281, 297
  - `.github/workflows/install-smoke.yml` lines 113, 214, 285, 295
  - `.github/workflows/npm-telegram-beta-e2e.yml` line 112
  - `.github/workflows/openclaw-live-and-e2e-checks-reusable.yml` line 639

  Most are intentional for ephemeral test images, but `docker-release.yml`'s 4 occurrences publish to GHCR and should carry SLSA provenance.

- **ghcr.io publish uses static `secrets.GITHUB_TOKEN`** at three sites in `docker-release.yml` (lines 89/93, 206/210, 317/321). Not OIDC-based registry auth.
- **No artifact-level attestation** for Docker images (`actions/attest-build-provenance` missing) or macOS DMG (`syft` + attest missing).
- **No `npm audit signatures`** runs in CI on PRs. Catches registry-signature regressions early; absent today.
- **No outbound-destination logging or allowlist** at the gateway level. A compromised dep phoning home (the canonical 2026 attack pattern: Shai-Hulud npm worm; Sapphire Sleet Axios compromise 2026-03-31) would not be detected from logs.
- **Secret rotation policy** is not codified per credential type. `SECURITY.md` documents the storage layout but not max age or rotation cadence.

### Risk classification

- **Docker image lacks provenance: High** — release-channel artifacts to GHCR with no verifiable build attestation. Downstream consumers cannot verify origin.
- **ghcr static token: Medium** — static `GITHUB_TOKEN` is short-lived per-job (good), but OIDC eliminates the broader trust class entirely. Investigation needed before flipping (see plan U6's investigation gate).
- **No `npm audit signatures` in CI: Medium** — catches a real and current attack class for ~10s of CI time per PR.
- **No outbound destination observability: Medium** — visibility-only; an attack that phones home would still succeed at execution but be noticed at egress.
- **In-process plugin trust + 1-entry denylist: Out of scope** — by design per `SECURITY.md`. Capability-declaration layer (plan U5) is the chosen mitigation; full process isolation is a future plan.

### What is missing

- **No externalized "what we said no to" register.** The deferrals/freezes/owner-only decisions are scattered across `AGENTS.md`, `SECURITY.md`, `CLAUDE.md` (symlink to `AGENTS.md`), and individual subtree `AGENTS.md` files. New-contributor (or future-self) triage requires re-deriving these. Plan U8 addresses this.

### Risk classification

- **Bus-factor exposure: Medium** — agent automation + CODEOWNERS substantially mitigate, but deferrals/freezes are not legible enough to make triage mechanical. A primary-maintainer absence would surface this as confusion, not as an outage — but at sustained cost.
- **Surface size in absolute terms: High but stable** — observation, not finding. Industry data places this firmly in the "Large surface" tier (multi-language, multi-platform, plugin ecosystem). Reducing it would be a strategic product decision, not a security remediation. The signal here is that **closing the SBOM/attestation gaps is _more_ important** for a project of this size, because each shipped artifact is a higher-blast-radius surface.

## 4. EU CRA Readiness Checklist

The EU Cyber Resilience Act ([Regulation (EU) 2024/2847](https://eur-lex.europa.eu/eli/reg/2024/2847/oj)) entered into force 2024-12-10. Vulnerability-reporting obligations bind **2026-09-11**. Full obligations including SBOM in technical documentation bind **2027-12-11**.

OpenClaw's classification is not yet legally established. As a network-connected developer tool with channel integrations, it is plausibly in Important Product Class II scope. **This audit assumes in-scope** for planning purposes; legal review should confirm.

| CRA requirement                                         | Current state                                                       | Gap                              | Plan unit             |
| ------------------------------------------------------- | ------------------------------------------------------------------- | -------------------------------- | --------------------- |
| Machine-readable SBOM in technical documentation        | ❌ bespoke JSON only                                                | Adopt CycloneDX 1.6 + SPDX 3.0.1 | U2                    |
| SBOM covers at least top-level dependencies             | ⚠️ ownership-only via `sbom-risk-report`                            | Generate full closure SBOM       | U2                    |
| Coordinated Vulnerability Disclosure process            | ✅ `SECURITY.md` reporting flow                                     | (none)                           | —                     |
| 24-hour exploited-vulnerability notification capability | ⚠️ `INCIDENT_RESPONSE.md` exists; CVD-channel binding to ENISA TBD  | Document ENISA-channel binding   | Out of scope for plan |
| Secure-by-default configuration                         | ✅ `gateway.bind="loopback"`, strict ws/wss, host-first sandbox-off | (none)                           | —                     |
| Update mechanism integrity                              | ✅ Sparkle EdDSA (macOS); npm provenance (CLI)                      | Docker image provenance          | U3/U4                 |
| Free security updates for support window                | ⚠️ implicit; no codified support-window policy                      | Document support window          | Out of scope for plan |
| Vulnerability handling process documentation            | ⚠️ `INCIDENT_RESPONSE.md` exists                                    | Add VEX curation workflow        | U7                    |

**Critical-path gap to 2026-09-11:** SBOM generation in CI (U2) + Docker provenance (U3+U4) must land before the vulnerability-reporting deadline so that a CRA-compliant disclosure can cite a reproducible SBOM and a verifiable artifact chain.

## 5. Methodology Notes

- **Static-only.** No runtime probing. Citations are file paths + line numbers as observed at HEAD `b84e57fca3` on 2026-04-25.
- **Source attribution.** Findings derive from a `ce-repo-research-analyst` scan + a `ce-best-practices-researcher` external scan, both run 2026-04-25, plus direct verification of every cited line/count by the author before publication.
- **Trust-model decisions are not findings.** Where `SECURITY.md` documents a deliberate posture (single-operator, in-process plugin trust), this audit notes it for context but does not classify it as a gap.
- **Re-run cadence: annual.** Surface counts and CI configurations drift; the next audit (`docs/security/audit-2027-04.md`) should re-derive the metrics in §3 from scratch and diff this document for closed/opened gaps.
